# Agent Ops — แจกงานให้ worker, สลับรุ่น, ประหยัด token

> ใช้ได้ทั้ง **Claude Code** และ **Antigravity** โดยไม่ขัดกับ Mentor Mode
> อ่านไฟล์นี้เมื่อ **เข้าโหมดด่วน**, **จะแจกงานให้ subagent/worker**, **งานไม่ผ่านการตรวจ**, หรือ **token ใกล้หมด**

---

## 1. ประหยัด token (ใช้เสมอ)

- ตัด output ก่อนเข้าแชต: ใช้ `tail`, `head`, `--stat`, แสดงเฉพาะบรรทัดที่ fail — log ยาวให้เขียนลงไฟล์ชั่วคราวแล้ว `grep`
- อ่านไฟล์เป็นช่วงบรรทัด ไม่อ่านทั้งไฟล์ถ้าไม่จำเป็น และไม่อ่านซ้ำสิ่งที่อยู่ในบทสนทนาแล้ว
- งานเปิดเว็บ/browser โยนให้ browser worker แทนตัวหลัก (ยกเว้นเช็คสั้นๆ) และใช้ข้อความหน้าเว็บ / accessibility tree แทน screenshot ถ้าต้องใช้ภาพให้ลดขนาดราวครึ่งหนึ่ง
- บทสนทนายาวมากแล้ว และงานถัดไปไม่เกี่ยวกัน ให้แนะนำผู้ใช้เปิด session ใหม่ (สถานะอยู่ใน `status.md` อยู่แล้ว)

## 2. แผนผังเครื่องมือและตารางเลือกรุ่น (Model Routing)

เลือกโมเดลตาม **"ผลลัพธ์ที่ต้องการ"** ไม่ใช่ตามเครื่องมือ และ **ต้องกำหนดรุ่นของ worker ทุกครั้ง** ห้ามปล่อยให้สืบทอดรุ่นแพงของตัวหลักโดยไม่ตั้งใจ

### เครื่องมือที่ตรงกันในแต่ละโปรแกรม

| หน้าที่ | Claude Desktop (Code tab) | Claude Code CLI / IDE | Antigravity |
|---|---|---|---|
| **แตก worker** | `start_session` / `Agent` tool | `Agent` tool | `invoke_subagent` |
| **ตั้งรุ่นตอนเรียก** | `model` / `set_session_model` | พารามิเตอร์ `model` | พารามิเตอร์ `Model` (`flash_lite`, `flash`, `pro`) |
| **ส่งข้อความต่อ** | `SendMessage` / `send_message` | `SendMessage` | `send_message` |
| **รอผล** | รอการแจ้งเตือน (ไม่ poll) | รอผล subagent | รอการแจ้งเตือนอัตโนมัติ (ไม่ poll) |

### ตารางเลือกรุ่นตามประเภทงาน

| ระดับ | Claude Code | Antigravity (`invoke_subagent`) | ใช้กับ |
|---|---|---|---|
| **fast (เร็ว)** | `haiku` | `flash_lite` หรือ `flash` (ใช้ `research` สำหรับอ่านอย่างเดียว) | หาข้อมูล: ไฟล์ X มีไหม, อ่าน log, grep, ค้นหลายไฟล์แบบอ่านอย่างเดียว |
| **standard (มาตรฐาน)** | `sonnet` | `flash` (งานโค้ดตาม spec ชัด) หรือ `pro` (งานโค้ดซับซ้อน) | ผลลัพธ์เป็นการตัดสินหรือโค้ด: ตรวจผ่าน/ไม่ผ่าน, วิเคราะห์, เขียนโค้ดตาม spec, แก้บั๊ก |
| **strong (แรง)** | `opus` | รุ่นหลักที่ผู้ใช้เลือก (Coordinator) | session หลักที่คุยกับผู้ใช้, วางแผน, งานที่ยังไม่ชัด — worker ขึ้นระดับนี้เฉพาะผ่าน Escalation ladder |
| **frontier (สูงสุด)** | `fable` / รุ่นสูงสุด | รุ่นสูงสุดของระบบ | ใช้เฉพาะเมื่อผู้ใช้สั่งหรืออนุญาตเท่านั้น |

**กติกาเพิ่มเติม:**
- **ประกาศก่อนเรียก (Announce):** ก่อนเรียก worker ทุกครั้ง ให้พิมพ์ 1 บรรทัดบอกผู้ใช้ว่าเรียก worker อะไร รุ่นไหน ทำอะไร
- **fast tier:** รุ่นเร็วอาจอ่านรายละเอียดเล็กพลาด (เช่น `*` สีแดง) ให้ระบุใน brief ว่าต้องตรวจซ้ำก่อนรายงานว่า "ไม่มี"
- **effort:** เริ่มที่ medium (งานอ่านอย่างเดียวใช้ low) เพิ่มเมื่อเห็นว่าจำเป็นเท่านั้น
- **จำกัดจำนวน:** ไม่เกิน **2 worker พร้อมกัน** (เริ่มจาก 1 ก่อน) และ **worker ห้ามแตก worker ต่อ** (ระบุใน brief ทุกครั้ง)
- **ห้ามแก้ไฟล์เดียวกันพร้อมกัน:** สองตัวห้ามแตะไฟล์เดียวกัน ให้ทำตามลำดับ หรือแยก worktree/workspace (`branch` / `share`)
- **ห้ามอ้างเกินจริง:** ห้ามบอกผู้ใช้ว่าสลับรุ่นหรือเรียก worker ถ้าไม่ได้เรียกผ่าน tool จริง ถ้าระบบไม่มีรุ่นที่ต้องการให้แจ้งตามตรง

## 3. เมื่อแจกงานให้ worker (Brief)

worker เริ่มใหม่และไม่เห็นบทสนทนา — brief คือข้อมูลทั้งหมดที่มันมี ต้องใส่ให้ครบ:
- **เป้าหมาย:** ไฟล์หรือส่วนที่รับผิดชอบ และระบุชัดว่า **อ่านอย่างเดียว** หรือ **แก้ไฟล์ได้**
- **ข้อห้าม:** ห้าม commit/push, อยู่ใน repo ที่ได้รับอนุญาต, ห้ามแตะ secret และ `.env`, ห้ามแตก worker ต่อ
- **ให้ข้อมูลที่รู้แล้วไปเลย:** path, branch, สัญญา API (field, message), gotcha ของโปรเจกต์ จะได้ไม่ต้องเสีย token ค้นใหม่
- **Self-check ก่อนรายงาน (บังคับทุกครั้งที่แก้โค้ด/เอกสาร):**
  1. อ่าน diff ตัวเองเทียบกับ spec ทีละข้อ
  2. grep หา helper / component / pattern ที่มีอยู่แล้วใน repo เพื่อนำมาใช้ซ้ำแทนการเขียนใหม่
  3. ตรวจว่าทำงานบนฐาน branch ที่ถูกต้อง ไม่ไปแตะการแก้ค้างของคนอื่น
  4. รายงานว่า self-check เจอและแก้อะไรไปบ้าง
- **คำสั่งตรวจที่ต้องรัน:** เช่น `typecheck`, `lint`, `test`
- **รายงานกลับ:** ไฟล์ที่เปลี่ยน, ผลคำสั่งตรวจจริง, สิ่งที่ยังไม่ได้ยืนยัน, ข้อความ commit พร้อมก๊อป (ถ้าเป็นงานแก้โค้ด)
- **ห้ามเดา:** ติดเรื่อง business rule หรือ API contract ให้ส่งคำถามกลับมาที่ตัวหลักเพื่อถามผู้ใช้

## 4. Escalation ladder — เมื่องานไม่ผ่านการตรวจ

ไต่ทีละขั้น ห้ามกระโดดไปรุ่นแพงทันที

1. **ส่งกลับให้ตรวจตัวเอง** บอกให้ชัดว่าข้อไหนไม่ผ่าน ให้เทียบกับแผนและ pattern เดิมใน repo (รุ่นและ effort เดิม)
2. **เพิ่ม effort 1 ระดับ** (low → medium → high)
3. **ขึ้นรุ่น 1 ระดับ** แล้วเริ่ม effort ต่ำใหม่ (Claude: `haiku` → `sonnet` → `opus` · Antigravity: `flash_lite` → `flash` → `pro`)
4. **รุ่นสูงสุด หรือ effort สูงสุด ต้องขอผู้ใช้ก่อน**

- ตัวหลักต้องตรวจ `git diff --stat` และผลคำสั่งตรวจจริงของ worker เสมอก่อนแจ้งผู้ใช้ว่า "เสร็จ"
- จดใน `<project>/log.md` ว่าขั้นไหนแก้ได้ เช่น `ladder: ขั้น 2 (เพิ่ม effort) ผ่าน` นานไปจะรู้ว่าค่าเริ่มต้นควรปรับไหม

---

## 5. ขอบเขตตามโหมด (ไม่ให้ขัด Mentor Mode)

- **โหมดเรียน (Mentor Mode — ค่าเริ่มต้น):**
  - ห้ามแตก worker ไปแก้โค้ดใน repo งานแทนผู้ใช้
  - แตก **fast worker** ได้เฉพาะงานค้นหา / อ่านไฟล์ / สำรวจโค้ดกว้างๆ
- **โหมดด่วน (Fast Mode):**
  - ใช้ **Standing Order** แตก worker ค้นหาและแก้โค้ดตามตารางรุ่นได้เลย **หลังผู้ใช้ตอบ "ลุย"** ในขั้นสรุปแผนแล้วเท่านั้น
- **ทั้ง 2 โหมด:**
  - ห้าม auto commit / push / เปิด MR / deploy / ย้ายการ์ดแทนผู้ใช้ (ผู้ใช้ทำเอง หรือสั่งเป็นครั้งๆ)
