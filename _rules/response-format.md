# รูปแบบคำตอบงานโค้ด (Mentor Mode + Step by Step)

> แยกจาก `AGENTS.md` เพื่อประหยัด token: AI อ่านไฟล์นี้ **เฉพาะเมื่อทำงานโค้ด** (ครั้งเดียวต่อ session) คำถามทั่วไปไม่ต้องอ่าน

## รูปแบบคำตอบเมื่อเสนอการแก้
1. **ปัญหาที่พบ** สาเหตุ ผลกระทบ และทำไมควรแก้
2. แต่ละ Change (Change 1, 2, 3 …) มี path และ 4 ส่วนเรียงกัน
   - **Before** คัดจากไฟล์จริงใน branch ปัจจุบัน
   - **After (diff)** code block ```` ```diff ```` (`+` เพิ่ม, `-` ลบ)
   - **After (อธิบาย)** โค้ด After ชุดเดียวกัน พร้อม comment `[เรียนรู้]` / `[ระวัง]` และสรุป 3 บรรทัด (input → process → output)
   - **After (copy)** โค้ดเต็มพร้อมวางแทน Before ได้ทันที
3. **สิ่งที่เปลี่ยน** logic, validation, ผลกระทบต่อระบบอื่น, trade-off
4. **วิธีแก้ด้วยตัวเอง** ขั้นตอนทีละ step + คำสั่งตรวจสอบ

- ห้ามใช้ `...` ซ่อนส่วนสำคัญ ห้ามตอบ "แก้ประมาณนี้"
- ถ้าตรวจไฟล์จริงไม่ได้ ให้บอกว่าขาดข้อมูลอะไร ห้ามสร้าง Before/After ขึ้นเอง

## รูปแบบคำตอบงาน (Step by Step)

**ใช้เมื่อไหร่**
- **ค่าเริ่มต้น:** งานที่ต้องเขียน/แก้โค้ด (ฟีเจอร์ใหม่, แก้บั๊ก, ขอ Step by Step) ให้ทำทีละขั้นตามรูปแบบนี้
- **ข้อยกเว้น ตอบรวดเดียว (แบบเดิม):** ถ้าแก้จุดเดียว (1 Change) หรือผู้ใช้พิมพ์ "ตอบรวดเดียว" ให้ตอบตาม "รูปแบบคำตอบเมื่อเสนอการแก้" ด้านบนในข้อความเดียว แล้วปิดด้วย **เช็กว่าผ่าน** และ **ต่อไป:**
- คำถามสั้นๆ หรือถามความรู้ ตอบตรงๆ ได้เลย

**สไตล์ (เลียนแบบ Claude Code — เรียบ อ่านง่าย)**
- ห้ามใช้ heading `#` `##` `###` และ emoji ประดับในแชต
- ขึ้นต้นคำตอบด้วยบรรทัดหัวเรื่อง `● **...**` บรรทัดเดียว
- **แผนใส่ในกล่องโค้ด (```) เสมอ ห้ามใช้ list** แต่ละบรรทัดขึ้นต้นด้วย `☐` ยังไม่ทำ · `▶` กำลังทำ · `☒` เสร็จ
- ผลตรวจขึ้นต้นบรรทัดด้วย `✓` ถูกต้อง · `✗` ต้องแก้ · `※` แนะนำเพิ่ม (ไม่ใช้ list ซ้อน)
- กล่องโค้ดสั้น (backtick) ใช้เฉพาะ path, คำสั่ง, URL และค่าที่ผู้ใช้ต้องพิมพ์จริง ชื่อ package หรือศัพท์ในประโยคไม่ต้องใส่
- ตัวหนาใช้เฉพาะ: บรรทัดหัวเรื่อง, **Change n**, **เช็กว่าผ่าน**, **ได้เรียนรู้:**, **ต่อไป:**
- อธิบายเป็นประโยคธรรมดา 1-2 บรรทัด ว่าทำอะไรและทำไม ไม่ต้องมีป้าย "ทำอะไร:" "ทำไม:"
- "ตรวจแล้ว / สมมติฐาน" ใส่เฉพาะตอนมีเรื่องที่ผู้ใช้ต้องรู้ (เช่น เวอร์ชันไม่ตรง, ความเสี่ยง)
- ปิดท้ายทุกคำตอบด้วยบรรทัดเดียว **ต่อไป:** ...

**1. คำตอบแรก = หัวงาน + ผลลัพธ์ที่จะได้ + แผน แล้วรอผู้ใช้ตกลง** (ยังไม่ให้โค้ด)
- **ผลลัพธ์ที่จะได้** ต้องมาก่อนแผนเสมอ ให้ผู้ใช้เห็นภาพปลายทางและยืนยันว่าตรงกับที่คาดไว้
  - งานหน้าจอ (UI): **ห้ามวาดกล่องด้วยตัวอักษร** (┌─┐ │ ฯลฯ) เพราะภาษาไทยทำให้เส้นเบี้ยว ให้เขียน 3 หัวข้อสั้นๆ แทน: **จะเห็นอะไร** (อยู่หน้าไหน ตรงไหนของจอ) · **กดแล้วเกิดอะไร** · **ได้อะไรออกมา**
  - งาน UI ใหญ่ (หน้าใหม่ทั้งหน้า หรือมีหลายส่วน): ทำไฟล์ตัวอย่าง `<project>/prototypes/<ชื่องาน>/index.html` (HTML ไฟล์เดียว ไม่มีข้อมูลจริง) ให้ผู้ใช้เปิดดูใน browser แล้วบอก path ในแชต
  - งาน API: ตัวอย่าง request และ response จริง (method, path, body, status code)
  - แก้บั๊ก: ตอนนี้เป็นอย่างไร → หลังแก้จะเป็นอย่างไร
  - งานอื่น: ผู้ใช้จะเห็น/ใช้อะไรได้เมื่อเสร็จ 2-3 ข้อ และสิ่งที่ **ไม่รวม** ในงานนี้ (ถ้ามี)
- ปิดด้วย **ต่อไป:** ถามว่าตรงกับที่คาดไว้ไหม ถ้าไม่ตรง ปรับผลลัพธ์และแผนก่อน ห้ามเริ่มขั้นที่ 1
````
● **งาน:** เพิ่ม API เช็กสถานะ server
`second-brain-todo` · branch `main`

**ผลลัพธ์ที่จะได้**
เปิด `http://127.0.0.1:4322/api/health` ใน browser แล้วเห็น
```json
{ "ok": true, "time": "2026-11-26T04:30:00.000Z" }
```
ใช้เช็กว่า server ยังทำงานอยู่ ยังไม่รวมการเช็กว่าอ่าน vault ได้

**แผน**
```
☐ 1. เขียน route /api/health
☐ 2. ทดสอบเรียกจาก browser
```
**ต่อไป:** ผลลัพธ์ตรงกับที่คาดไว้ไหม · ถ้าตรงพิมพ์ "เริ่ม" · ไม่ตรงบอกได้เลยว่าอยากได้แบบไหน
````

**2. ให้ทีละ 1 ขั้น** ห้ามเททุกขั้นมาในคำตอบเดียว
````
● **ขั้นที่ 1/2 · เขียน route /api/health**
```
▶ 1. เขียน route /api/health
☐ 2. ทดสอบเรียกจาก browser
```
เพิ่ม route ที่ตอบว่า server ยังทำงานอยู่ ใช้เช็กเร็วๆ ว่าระบบพร้อมก่อนทำส่วนอื่น

**สิ่งที่ต้องทำ**
1. เปิด `src/app.ts` แล้วแก้ตาม Change 1
2. เปิด terminal ใน VS Code (Ctrl+`) ที่โฟลเดอร์ `second-brain-todo` แล้วรัน
```powershell
npm run typecheck   # [เรียนรู้] ตรวจ type ทั้งโปรเจกต์ ไม่รัน server
```

**Change 1** `src/app.ts:8`
(Before / After (diff) / After (อธิบาย) / After (copy) ตามรูปแบบด้านบน)

**เช็กว่าผ่าน**
1. `npm run typecheck` ไม่มี error

**ต่อไป:** เขียนเสร็จแล้วพิมพ์ "เสร็จแล้ว ตรวจสอบโค้ดให้หน่อย"
````

**กฎของทุกขั้น (Mentor Mode = ผู้ใช้ทำตามได้เองโดยไม่ต้องเดา)**
- **ตรวจตัวเองก่อนส่ง (self-check):** ก่อนเสนอโค้ดใหม่ ให้ `grep` หา helper / component / pattern ที่มีอยู่แล้วใน repo ถ้ามีให้ใช้ของเดิม ห้ามเขียนซ้ำ และอ่าน diff ของตัวเองเทียบกับแผนทีละข้อ
- **คำสั่ง terminal อยู่ในแชตเสมอ** (สร้างโฟลเดอร์, `npm init`, `npm install`, migrate ฯลฯ) ในกล่องโค้ด พร้อมบอกว่ารันที่ไหน (PowerShell / terminal ใน VS Code / โฟลเดอร์ไหน) และ comment `# [เรียนรู้]` สั้นๆ ว่าแต่ละคำสั่งทำอะไร ห้ามเขียนแค่ "ลง X" หรือ "ติดตั้ง Y" โดยไม่ให้คำสั่ง
- **มี "สิ่งที่ต้องทำ" เป็นข้อ 1, 2, 3** เรียงตามลำดับที่ผู้ใช้ต้องลงมือ (เปิดอะไร → รันอะไร → แก้ไฟล์ไหน) ให้ผู้ใช้ไล่ทำได้ทันที
- ถ้าโค้ดยาวอยู่ในไฟล์คู่มือ ต้องบอกให้ชัดว่า **เริ่มที่หัวข้อไหน** (เช่น "Change 0 บรรทัด 53") คำสั่ง terminal ยังต้องอยู่ในแชตด้วย

**3. เมื่อผู้ใช้พิมพ์ "เสร็จแล้ว ตรวจสอบโค้ดให้หน่อย"** (หรือ "เสร็จแล้ว", "ตรวจให้หน่อย")
- เปิดไฟล์จริงและ `git diff` ของขั้นนั้น ห้ามตรวจจากความจำ
- เช็กด้วยว่าผู้ใช้เขียนซ้ำกับ helper / component ที่มีอยู่แล้วไหม ถ้าซ้ำให้ ✗ พร้อมชี้ของเดิม
- รันคำสั่งตรวจที่ไม่แก้ไฟล์ได้ (typecheck, lint, test) ถ้ารันไม่ได้ให้บอกผู้ใช้ว่าควรรันอะไร
````
● **ตรวจขั้นที่ 1/2** · ✓ 1 · ✗ 1
✓ `src/app.ts:8` ใช้ res.json ถูกต้อง header เป็น JSON ให้เอง
✗ `src/app.ts:9` พิมพ์ toISOString ตก s ทำให้ typecheck ไม่ผ่าน
```diff
-  res.json({ ok: true, time: new Date().toISOtring() })
+  res.json({ ok: true, time: new Date().toISOString() })
```
**ต่อไป:** แก้จุด ✗ แล้วพิมพ์ "เสร็จแล้ว ตรวจสอบโค้ดให้หน่อย" อีกครั้ง
````
- **ผ่านหมด (ไม่มี ✗)** → หัวเรื่องเป็น `● **ตรวจขั้นที่ n/N** · ✓ x · ผ่าน` อัปเดตแผน (☒ ขั้นนั้น, ▶ ขั้นถัดไป) แล้วให้ขั้นถัดไปในข้อความเดียวกันเลย
- **มี ✗** → อยู่ขั้นเดิม ชมจุดที่ถูกตามจริงเสมอ

**4. จบงาน**
````
● **สรุปงาน** · เสร็จ 2/2
```
☒ 1. เขียน route /api/health
☒ 2. ทดสอบเรียกจาก browser
```
**ได้เรียนรู้:** route GET ใน Express, การใช้ res.json, ตั้งชื่อตัวแปรที่ไม่ใช้ด้วย _
**ต่อไป:** พิมพ์ "จบงาน" เพื่อบันทึก status หรือสั่งงานถัดไปได้เลย
````

**5. เนื้อหายาว → ทำเป็นไฟล์ `.md`**
- ถ้าแผนเกิน 5 ขั้น, มีมากกว่า 3 Change, หรือคำตอบจะยาวเกิน ~150 บรรทัด ให้เขียนคู่มือทั้งงานลง `<project>/guides/YYYY-MM-DD-<ชื่องาน>.md` ตาม `_templates/task-guide.md` (ในไฟล์ใช้ heading ได้ตามปกติ)
- ในแชตแสดงแค่หัวเรื่อง + แผน + ขั้นปัจจุบันแบบสั้น แล้วบอก path ของไฟล์ให้ผู้ใช้กดเปิด (VS Code: Ctrl+คลิก หรือเปิดใน Obsidian)
- ตรวจผ่านแต่ละขั้นแล้ว ให้ติ๊ก `[x]` ในไฟล์ด้วย ไฟล์จึงเป็นตัวบอกความคืบหน้าจริง
- ถ้าผู้ใช้สั่ง implement เอง AI แก้โค้ดได้ แต่ยังรายงานทีละขั้นตามรูปแบบเดียวกัน พร้อม **เช็กว่าผ่าน**
