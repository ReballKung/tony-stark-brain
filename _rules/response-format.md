# รูปแบบคำตอบงานโค้ด (v3 · Markdown UI)

> AI อ่านไฟล์นี้ **เฉพาะเมื่อทำงานโค้ด** (ครั้งเดียวต่อ session) คำถามทั่วไปตอบตรงๆ ด้วย Markdown กระชับ ไม่ต้องใช้แม่แบบ

## 1. หลักการ

- ลำดับความสำคัญ: ถูกต้อง → ปลอดภัย/เข้าใจบริบท → ขั้นตอนชัด → อ่านง่าย → สวยงาม ห้ามให้การตกแต่งทำให้ยาวขึ้นโดยไม่จำเป็น
- หัวข้อในแชตใช้ `###` · คั่นกลุ่มใหญ่ด้วย `---` เท่าที่จำเป็น · checklist ใช้ `- [ ]` / `- [x]` · code block ระบุภาษาเสมอ (`ts` `json` `powershell` `diff` …)
- inline code เฉพาะ path, API, ตัวแปร, คำสั่ง · ตัวหนาเฉพาะชื่อสถานะและประเด็นสำคัญ · ตารางเฉพาะตอนเปรียบเทียบจริง · ห้าม HTML/CSS/ANSI และห้ามวาดกล่องด้วยตัวอักษร (┌─┐ ภาษาไทยทำให้เส้นเบี้ยว)
- Emoji ใช้ 1 ตัวต่อหัวข้อ ตามชุดนี้เท่านั้น: 🚀 งานใหม่ · 🎯 ผลลัพธ์ · 🗺️ แผน · 🛠️ ขั้นตอน · 📝 สิ่งที่ต้องทำ · 💻 คำสั่ง · 🔧 Change · 🔍 ตรวจ · ✅ ผ่าน · ❌ ไม่ผ่าน · ⚠️ ระวัง · 🧪 ทดสอบ · 🐛 Feedback · ❓ คำถาม · 🎉 จบงาน · 🎓 ได้เรียนรู้ · ➡️ NEXT ACTION
- ทุกคำตอบใน workflow จบด้วย `### ➡️ NEXT ACTION` บอกขั้นถัดไปขั้นเดียว พร้อมคำที่ผู้ใช้ต้องพิมพ์ตรงตัว
- ห้ามบอกว่าผ่าน/รันแล้ว/ตรวจแล้ว ถ้ายังไม่ได้ทำจริง · แยก **ตรวจแล้ว** กับ **สมมติฐาน** · ห้าม `...` ซ่อนส่วนสำคัญ · ห้าม "แก้ประมาณนี้" · ตรวจไฟล์จริงไม่ได้ให้บอกว่าขาดอะไร ห้ามสร้าง Before เอง
- ใช้แม่แบบให้ตรงสถานะ ห้ามผสม (เช่น จบงานทั้งที่ยังมี FAIL)

| เหตุการณ์ | แม่แบบ |
|---|---|
| ได้งานใหม่ | 1. คำตอบแรก |
| ผู้ใช้พิมพ์ "เริ่ม" / ผ่านขั้นก่อนแล้ว | 2. ทีละขั้น |
| ผู้ใช้พิมพ์ "เสร็จแล้ว ตรวจสอบโค้ดให้หน่อย" | 3. ตรวจโค้ด |
| ทุกขั้นผ่าน | 4. จบงาน |
| ผู้ใช้พิมพ์ "Feedback: ..." | 5. Feedback |
| ผู้ใช้พิมพ์ "คำถาม : ..." / "คำถาม: ..." | ตอบข้อสงสัย (ไม่แก้ไฟล์ / ไม่เปลี่ยนขั้นงาน) |

ข้อยกเว้น **ตอบรวดเดียว:** แก้จุดเดียว (1 Change) หรือผู้ใช้พิมพ์ "ตอบรวดเดียว" → ใช้แม่แบบ 2 ครั้งเดียวจบ (ไม่ต้องมีความคืบหน้า) โหมดด่วนดู `_rules/fast-mode.md`

## 2. Change (ใช้ในแม่แบบ 2 และ 5)

**โหมดเรียน (ค่าเริ่มต้น) = 4 ส่วน**
- **Before** คัดจากไฟล์จริงใน branch ปัจจุบัน
- **After (diff)** ```` ```diff ```` `+` เพิ่ม `-` ลบ บรรทัดที่แก้ให้ `-` เดิมแล้ว `+` ใหม่
- **After (อธิบาย)** โค้ดชุดเดียวกัน + comment ตามภาษา (`//` `<!-- -->` `--` `#`) ขึ้นต้น `[เรียนรู้]`
  - หัว block 1-2 บรรทัด: ทำหน้าที่อะไร ถูกเรียกจากไหน
  - บรรทัดที่ไม่ชัด: ทำอะไร และทำไม (ทำไม `await`, ทำไมต้อง transaction)
  - แนวคิดใหม่ตั้งชื่อให้ค้นต่อได้ เช่น `[เรียนรู้] Guard clause: ...`
  - จุดพลาดบ่อยขึ้นต้น `[ระวัง]` บอกว่าผิดแล้วเกิดอะไร · ไม่ comment บรรทัดที่อ่านเข้าใจเอง
  - ปิดด้วย **สรุป:** input → process → output
- **After (copy)** โค้ดเต็ม ไม่มีเครื่องหมาย ไม่มี comment เรียนรู้ วางแทน Before ได้ทันที

**งานเล็กมาก / โหมดด่วน** → Before + After หรือ diff อย่างเดียวได้ + **เหตุผลที่แก้**

```ts
// [เรียนรู้] หา Private Class ที่ผู้เรียนซื้อ แล้วคืนวันหมดอายุใหม่ — เรียกจาก RenewalController.renew()
async function extendExpiry(userId: number, classId: number, days: number) {
  // [เรียนรู้] Guard clause: ข้อมูลไม่ถูกให้หยุดทันที ไม่ต้องไปถึง DB
  if (days <= 0) throw new BadRequestException('days must be > 0');
  // [ระวัง] ต้องเช็กทั้ง userId และ classId ไม่งั้นต่ออายุแทนคนอื่นได้ (IDOR)
  const enrollment = await repo.findOne({ where: { userId, classId } });
}
```

## 3. แม่แบบ 1 — คำตอบแรก (ยังไม่ให้โค้ด)

- **ผลลัพธ์ที่จะได้มาก่อนแผนเสมอ** · UI: จะเห็นอะไร (หน้าไหน ตรงไหน) / กดแล้วเกิดอะไร / ได้อะไร · UI ใหญ่: ทำ `<project>/prototypes/<งาน>/index.html` แล้วบอก path · API: request + response จริง · บั๊ก: ตอนนี้ → หลังแก้ · อื่นๆ: 2-3 ข้อ + สิ่งที่ **ไม่รวม**

## 4. แม่แบบ 2 — ทีละขั้น (ให้ทีละ 1 ขั้นเท่านั้น)

- ก่อนส่ง: `grep` หา helper / component / pattern เดิมใน repo ถ้ามีให้ใช้ของเดิม และอ่าน diff ตัวเองเทียบแผน
- **สิ่งที่ต้องทำ** เรียงตามลำดับลงมือ (เปิดอะไร → แก้ไฟล์ไหน → รันอะไร)

## 5. แม่แบบ 3 — ตรวจโค้ด

- เปิดไฟล์จริง + `git diff` ของขั้นนั้น ห้ามตรวจจากความจำ · เช็กว่าเขียนซ้ำของเดิมไหม (ซ้ำ = FAIL พร้อมชี้ของเดิม)
- รันคำสั่งตรวจที่ไม่แก้ไฟล์ได้ (typecheck, lint, test) รันไม่ได้ให้บอกว่าควรรันอะไร และระบุ **ขอบเขตการตรวจ**
- จัดกลุ่ม ✅ PASS / ❌ FAIL / ⚠️ WARNING กลุ่มละหัวข้อเดียว รายการละ 1 บรรทัด (`ไฟล์:บรรทัด` + เหตุผล) ไม่มีรายการให้ข้ามกลุ่มนั้น
- **ไม่มี FAIL** → หัวเรื่อง `· ผ่าน` ติ๊ก `[x]` ในแผน (และในไฟล์ guide) แล้วให้ขั้นถัดไปตามแม่แบบ 2 ในข้อความเดียวกัน หรือแม่แบบ 4 ถ้าเป็นขั้นสุดท้าย
- **มี FAIL** → อยู่ขั้นเดิม ชมจุดที่ถูกตามจริงเสมอ

````markdown
### 🔍 ตรวจขั้นที่ 1/2 · 1 PASS · 1 FAIL
ขอบเขต: อ่านโค้ด + `npm run typecheck`

### ✅ PASS
- `src/app.ts:8` ใช้ res.json ถูกต้อง header เป็น JSON ให้เอง

### ❌ FAIL
- `src/app.ts:9` พิมพ์ toISOString ตก s ทำให้ typecheck ไม่ผ่าน
```diff
-  res.json({ ok: true, time: new Date().toISOtring() })
+  res.json({ ok: true, time: new Date().toISOString() })
```

---

### ➡️ NEXT ACTION
แก้จุด ❌ แล้วพิมพ์ **"เสร็จแล้ว ตรวจสอบโค้ดให้หน่อย"** อีกครั้ง
````

## 7. แม่แบบ 5 — Feedback (ใช้ได้ทั้งโหมดเรียนและโหมดด่วน)

**แบบ A — ปัญหาในงาน/โค้ด**
- ข้อมูลไม่พอ ถามกลับข้อเดียวรวบ: ทำอะไร · คาดว่าเห็นอะไร · เห็นอะไรจริง · error / screenshot
- สถานะ: `กำลังตรวจ` / `เจอสาเหตุ` / `เสนอการแก้` / `แก้แล้ว` · ยังไม่รู้สาเหตุให้เก็บข้อมูลก่อน ห้ามรีบเสนอ patch
- โหมดเรียน: เสนอ Change ให้แก้เอง · โหมดด่วน: แก้ให้เลยแล้วรายงานว่าทดสอบอะไร ได้ผลอะไร
- ปัญหามาจากขั้นที่ผ่านไปแล้ว → เปลี่ยนขั้นนั้นกลับเป็น `[ ]` (และในไฟล์ guide) จนแก้ผ่าน

**สาเหตุ (ตรวจแล้ว):** `src/users/export.ts:24` ส่ง filter ว่างไป query เลยไม่เจอผู้ใช้

(4 ส่วนตามข้อ 2)

### 🧪 เช็กว่าผ่าน

**แบบ B — ข้อติเรื่องระบบ Second Brain / รูปแบบคำตอบ**
- ไม่แก้กฎทันที เพิ่ม 1 บรรทัดท้าย `feedback.md` ที่ root ของ vault (ไม่มีให้สร้าง): `- YYYY-MM-DD [เครื่องมือ] <ข้อติ> → <ข้อเสนอแก้>`
- ตอบ 1-2 บรรทัดว่าจดแล้ว ถ้าปรับในงานนี้ได้ทันทีให้ปรับเลย
- ผู้ใช้พิมพ์ "รวม feedback" → สรุป `feedback.md` เป็นกลุ่ม แล้วเสนอแก้กฎทีเดียว

### ❓ คำสั่ง `"คำถาม : ..."` (หรือ `"คำถาม: ..."`)
- ใช้เมื่อผู้ใช้สงสัยอะไรระหว่างทำงาน (ใช้ได้ทั้งโหมดเรียนและโหมดด่วน)
- **ห้ามแก้ไฟล์, ห้ามสร้างการ์ดบนบอร์ด To Do, ห้ามสั่ง worker แก้โค้ด, ห้ามเปลี่ยนสถานะขั้นงานที่ค้างอยู่**
- ตอบตรงประเด็นด้วยภาษาพูดเข้าใจง่าย ไม่ต้องใช้แม่แบบ Change 4 ส่วน · ถ้าถามเกี่ยวกับโค้ดให้ตรวจไฟล์จริงก่อนตอบ (ใช้ fast worker ค้นหาได้ถ้าต้องค้นกว้าง)
- ถ้ามีงานค้างอยู่ในแชต ปิดท้ายด้วย `### ➡️ NEXT ACTION` 1 บรรทัดเพื่อกลับไปทำขั้นเดิมต่อ (เช่น กลับไปทำขั้นที่ X ต่อ หรือพิมพ์ `"คำถาม : ..."` เพิ่มได้)

## 8. เนื้อหายาว → ไฟล์ guide

- แผนเกิน 5 ขั้น, เกิน 3 Change หรือยาวเกิน ~150 บรรทัด → เขียนทั้งงานลง `<project>/guides/YYYY-MM-DD-<ชื่องาน>.md` ตาม `_templates/task-guide.md`
- ในแชตแสดงแค่หัวเรื่อง + ความคืบหน้า + ขั้นปัจจุบันแบบสั้น + path ไฟล์
- ตรวจผ่านแต่ละขั้นแล้วติ๊ก `[x]` ในไฟล์ด้วย ไฟล์จึงเป็นตัวบอกความคืบหน้าจริง
- ผู้ใช้สั่ง implement เอง AI แก้โค้ดได้ แต่ยังรายงานทีละขั้นตามแม่แบบเดียวกัน
